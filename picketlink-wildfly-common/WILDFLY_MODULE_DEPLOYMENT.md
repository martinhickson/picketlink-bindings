# PicketLink on WildFly: module-layer deployment

## Recommendation

Deploy all PicketLink libraries as a **single WildFly module** (`org.picketlink`). Application WARs declare a module dependency only; they do not embed PicketLink JARs in `WEB-INF/lib`.

## Why one module (`org.picketlink`)?

Separate modules (e.g. `org.picketlink.federation` + `org.picketlink.wildfly-common`) are only useful when you need **independent versioning** or **optional components** (federation without WildFly bindings). For WildFly 36 + Elytron SAML SP/IDP, everything loads together in one class loader, so a single module is simpler:

- One `module.xml`, one install step, one `jboss-deployment-structure` dependency
- No cross-module visibility rules between federation and bindings
- Matches how integration tests stage PicketLink: all runtime JARs under `modules/org/picketlink/main/`

WildFly loads each JAR via an explicit `<resource-root path="…"/>` entry in `module.xml` (generated by `PicketLinkModuleInstaller` from the staged JAR list).

## Why not embed PicketLink in the WAR?

| Problem | Cause |
|---------|--------|
| `NoClassDefFoundError: ElytronHttpExchange` | Elytron web classes exist only in WildFly system modules, not in `WEB-INF/lib` |
| Duplicate `SPFormAuthenticationMechanism` types | Elytron mechanism (module) vs Undertow extension (deployment) use different class loaders |
| Reflection / TCCL / deferred-completion workarounds | Split loaders between Elytron HTTP layer and Undertow SAML mechanism |

Tomcat/Jetty can keep JARs in the WAR; WildFly Elytron cannot.

## Module layout (IT and production)

```
$JBOSS_HOME/modules/org/picketlink/main/
  module.xml
  picketlink-wildfly-common-*.jar
  picketlink-federation-*.jar
  picketlink-common-*.jar
  … (runtime transitive dependencies)
```

`module.xml` declares dependencies on WildFly-provided APIs:

- `org.wildfly.security.elytron`
- `org.wildfly.security.elytron-web.undertow-server`
- `org.wildfly.security.elytron-web.undertow-server-servlet`
- `io.undertow.core`, `io.undertow.servlet`
- `jakarta.servlet.api`, `org.jboss.logging`

JARs already supplied by those modules (e.g. `jboss-logging`, `jakarta.servlet-api`) are **not** copied into `org.picketlink`.

## WAR deployment descriptor

```xml
<jboss-deployment-structure xmlns="urn:jboss:deployment-structure:1.2">
    <deployment>
        <dependencies>
            <module name="org.picketlink" services="export"/>
        </dependencies>
    </deployment>
</jboss-deployment-structure>
```

`services="export"` exposes `META-INF/services/io.undertow.servlet.ServletExtension` so Undertow registers `SPServletExtension` / `IDPServletExtension` from the module.

WAR contents: `web.xml`, `picketlink.xml`, `jboss-web.xml`, and **application-specific** classes only.

## ACS URL

SAML responses POST to `{ServiceURL}j_security_check` (configured in `SPFormAuthenticationMechanism.resolveAssertionConsumerServiceUrl()`). That URL is handled by the same module-loaded form/Elytron mechanism that started SSO.

## Integration test wiring

1. `maven-dependency-plugin` copies runtime libs to `target/test-libs`
2. `PicketLinkModuleInstaller` (pre-integration-test) stages `org.picketlink` under `${jboss.home}/modules`
3. `ElytronTestSetup` references module name `org.picketlink` for Elytron realm and HTTP mechanism factory
4. `SamlDeployments` builds thin WARs with `jboss-deployment-structure.xml` only
